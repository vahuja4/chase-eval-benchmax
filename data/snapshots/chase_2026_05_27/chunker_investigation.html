Issue 1: Why p_00087's first chunk absorbed the full first FAQ answer

The raw text (first 3 lines)

line 0  [3 words]:  Chase Overdraft Services
line 1  [69 words]: Frequently Asked QuestionsWith Chase Overdraft Assist℠, we won't
                    charge an Overdraft Fee if you're overdrawn by $50 or less ...
line 2  [46 words]: Chase Overdraft Assist does not require enrollment and comes
                    with all Chase checking accounts except ...
Root cause: extraction concatenation Trafilatura glued "Frequently Asked Questions" directly to "With Chase Overdraft Assist..." with no whitespace or newline between them. The result is a single 69-word line. The heading detector operates line-by-line, so it never sees "Frequently Asked Questions" as a separate line — it sees one long line starting with "Frequently Asked QuestionsWith..." which fails the ≤8-word check.

What the chunker does with it

  1. "Chase Overdraft Services" (3 words, ~4 tokens) → is_heading = True, but current_tokens = 0 < MIN_TOKENS (20) → no break, starts accumulating.
  2. "Frequently Asked QuestionsWith..." (69 words, ~95 tokens) → is_heading = False (too many words). current_tokens = 4, adding 95 doesn't exceed 400 → appended.
  3. Lines keep appending until the 400-token cap forces a hard break at 369 tokens.

Fix options
  1. Extraction-level fix (preferred): In src/extract.py, post-process the text to split lines where a short title-case prefix is immediately followed by a capital letter starting a new sentence (e.g., split on the regex boundary (?<=[a-z])(?=[A-Z][a-z]) when preceded by ≤5 title-case words). This fixes p_00087 and catches similar glued headings elsewhere.
  2. Chunker-level fix: In chunk_page(), before the main loop, pre-split long lines that match a "heading prefix + sentence start" pattern. One-line addition but pushes extraction concerns into the chunker.

This is a one-page issue — the other 6 FAQ pages have correct line breaks. The extraction fix is still worthwhile because the broader scan found ~69 lines with similar concatenation across the corpus (though most are brand-name compounds like DashPass, not heading+content gluing).

Issue 2: Heading detector for short noun-phrase titles

Current behavior

def is_heading(line):
    words = line.split()
    if line.startswith("- ") or line.startswith("* "):
        return False
    if stripped.endswith("?") and len(words) <= 15:
        return True            # questions are headings
    if len(words) > 8:
        return False           # too long
    if stripped.endswith((".", "!")) and len(words) > 4:
        return False           # declarative sentences
    return True                # short line = heading

The detector already catches these correctly All short noun-phrase titles (1–8 words, not ending in . or !) are detected as headings. They trigger a chunk break whenever current_tokens ≥ MIN_TOKENS (20).

Where it fails

The heading detector itself is fine. The failures come from two other causes:

  1. Concatenation (Issue 1): The heading is glued to the next paragraph on the same line, so the detector never sees it. Fix belongs in extraction.
  2. Low accumulation: When a heading follows only ~4–15 tokens of prior content (e.g., a page title), current_tokens < 20 prevents a break. The heading merges into the growing chunk. This is by design — preventing fragments — but it means a chunk can start with a page title + section heading + content all merged together.
Possible tweak for (2) Lower the break threshold from 20 to, say, 10 tokens specifically when the incoming line matches a strong heading pattern (all-title-case, ≤4 words). This would let page titles like "Chase Overdraft Services" (4 tokens) stand as their own chunk-start, with the section heading breaking right after. However, this risks creating more sub-20-token fragments. The merge pass would catch most of them, but it's a tradeoff. Verdict: not clearly worth it. The 20-token threshold is doing its job for the majority of cases.

Verdict

No-op — do not raise the merge threshold.

Raising MIN_TOKENS would force the 23-token APR/fee chunks to merge into adjacent content, destroying their usefulness as standalone factual units. The breakdown:

  • 40% (12/30) are factual or structured data — short because the fact IS short (an APR, a fee waiver rule, a benefit limit). These are the best QA material in the whole corpus. Merging them would dilute them.
  • 27% (8/30) are thin — heading + topic sentence with no specific fact. These are low-value but harmless. The info-density classifier in Step 1.7 should flag most of them as low-info.
  • 33% (10/30) are marketing — taglines, CTAs, promotional copy. These should be caught by the info-density classifier and/or boilerplate dedup. Raising the merge threshold wouldn't help — it would just create 60-token marketing chunks instead of 30-token ones.
The right filter is downstream, not here. The info-density classifier (Step 1.7) is designed to flag the marketing and thin chunks. Raising the merge threshold would sacrifice the good short factual chunks to eliminate bad ones that are better handled by the classifier. Leave MIN_TOKENS = 20.
