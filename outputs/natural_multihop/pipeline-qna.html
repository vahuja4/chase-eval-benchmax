Pipeline Explainer — Q&A

Questions and answers about the eval generation pipeline, covering execution model, corpus sampling, diversity mechanisms, and chunk linking.

Q1 What does "Micro-batch — Dynamic sizing, checkpointed, resumable" mean?

Micro-batch means the pipeline doesn't generate all QA pairs in one shot. It works in small groups — say 5 at a time. Each batch goes through the full cycle (generate, filter, regenerate) before the next batch starts.

The three properties describe how those batches behave:

  • Dynamic sizing — before each batch, the pipeline checks how many questions of each type it still needs. If the target is 15 multi-hop pairs and 12 are already done, the next batch only generates 3, not another full 5. The batch size adapts to what's remaining.
  • Checkpointed — progress is saved after each batch completes. If 3 batches have finished and produced 10 good QA pairs, that state is persisted to disk.
  • Resumable — if the pipeline crashes, times out, or is stopped mid-run, it can be restarted and picks up from the last checkpoint instead of regenerating everything from scratch.

The alternative would be generating all questions at once in a single large call, which is fragile (one failure loses everything), wasteful (might generate 30 questions when only 15 are needed after filtering), and non-adaptive (can't adjust the mix based on what's already passed).

Q2 What is the purpose of drawing a diverse profile sample from the corpus?

The pipeline can't afford to process the entire corpus through an LLM — that would be slow and expensive. So it draws a representative sample up front and uses it for three things:

  1. Corpus profiling — the sample is fed to an LLM that writes a structured summary of what the corpus is about (domain, vocabulary, document types). That summary is then injected into every generation prompt so the question-writing LLM has domain context.
  2. Entity extraction — KeyBERT runs over the sample to build entity indices (which chunks mention which entities, which entities co-occur). These indices help the linker find meaningful cross-document connections later.
  3. Seed chunk selection — the chunks in this sample become the pool from which the pipeline picks "primary chunks" (starting points) for QA generation. Since the sample was drawn to maximize diversity, the generated questions cover the breadth of the corpus rather than clustering around a few popular articles.
Q3 What exactly ensures diversity in the sampling?

Two mechanisms work together, at different stages:

Mechanism 1 — Stratified document sampling

The function diverse_profile_sample() draws a pool of chunks (roughly 5% of the corpus, capped between 500–10,000). The budget is split in half:

  • First half — stratified by document. Chunks are grouped by document ID. Each document gets at least 1 chunk, with the rest distributed proportionally. This guarantees that even a small document gets representation alongside a large one.
  • Second half — random fill. The remaining budget is filled randomly from chunks not already selected, adding volume without sacrificing the coverage guarantee.

For example, with 50 Chase.com help articles and a budget of 500 chunks: roughly 250 are spread across all 50 articles (at least ~5 per article), and the other 250 are random.

Mechanism 2 — Greedy max-diversity selection

When the pipeline needs a small subset from that pool (e.g., 4–8 chunks to show the profiling LLM), the function select_diverse() uses a Jaccard distance algorithm:

  • Each chunk is tokenized into a set of lowercased words.
  • The seed is the chunk with the largest vocabulary (most unique tokens).
  • Each subsequent pick maximizes the minimum Jaccard distance to all already-selected chunks.
  • Any candidate below 0.3 Jaccard distance from an existing pick is rejected as too similar.

This ensures the few chunks the profiling LLM actually sees are as textually different from each other as possible — not just from different documents, but covering different vocabulary and topics.

In short: stratified sampling ensures every document is represented in the pool; Jaccard-based greedy selection ensures the chunks fed to the LLM are maximally diverse in content.

Q4 How does the metadata linker find related chunks without any LLM calls?

It generates search queries from the primary chunk's own structure, runs those queries against the corpus search index, and then filters and ranks the results. No LLM is involved at any point — it's entirely deterministic.

Query generation (4 strategies, in priority order)
  • Header-context queries — extracts values from the chunk's metadata keys (h1, h2, h3, section_header, title). These are the most precise signal because they're structural labels the document already carries.
  • Code-pattern regex matches — runs discriminative entity patterns (regexes identified during corpus profiling) against the chunk text. Matched tokens become search queries.
  • Compound entity queries — takes up to 4 entities found in the chunk and generates pairwise combinations (e.g., "Chase Sapphire balance transfer"). This finds chunks that share multiple related concepts rather than just one keyword.
  • TF-IDF keyphrases — corpus-informed keyword extraction. Because TF-IDF is computed against the corpus's document frequencies, it favours terms that are distinctive to this chunk rather than common across the corpus.
Post-search filtering pipeline

Search results go through several filters before ranking:

  • The primary chunk itself is excluded
  • Chunks shorter than 400 characters are dropped
  • Same-file chunks are excluded (unless in "sequential" reasoning mode)
  • Chunks already used by prior questions are skipped (cross-question dedup)
  • A coherence floor requires at least 15% Jaccard token overlap with the primary — removes completely unrelated results
  • A similarity ceiling of 55% Jaccard against the primary — removes near-duplicates that would make the question trivial
Ranking and selection

Surviving candidates are scored with a composite: 40% search relevance + 30% Jaccard coherence + 30% entity overlap (with an optional wiki co-occurrence boost). Candidates are then picked greedily, skipping any whose Jaccard similarity to an already-selected secondary exceeds 0.55. This prevents the anchor bundle from containing two chunks that say nearly the same thing.

Retry mechanism

If confidence after the first pass is below 0.5 (meaning not enough good secondaries were found), the linker generates a second round of queries from the chunk's body text — specifically the first sentence and the longest capitalized multi-word phrase (likely a product or feature name). These results are merged into the candidate pool and selection runs again.

Q5 How does the search agent linker work, and how does it relate to the metadata linker?

The search agent linker is a hybrid — it always runs the metadata linker first (which is free), then decides whether to also invoke an LLM for deeper exploration.

Decision to use the LLM

The LLM path fires if either condition is true:

  • The metadata linker returned low confidence (below 0.5) — meaning it couldn't find enough good secondaries with heuristics alone
  • This item was randomly selected by search_agent_pct — e.g. at 1.0, every item goes through the LLM regardless of metadata confidence

If neither condition is met, the metadata linker's result is returned as-is — the LLM is never called.

LLM linking flow

When the LLM path fires:

  1. The primary chunk's content (up to 4,000 characters) is sent to an LLM via a rollout server
  2. The LLM runs as an agent with corpus search tools — it can call semantic search, keyword search, and hybrid search against the actual corpus
  3. It explores iteratively over multiple turns (configurable via max_turns and max_tool_calls), reading search results and refining its queries
  4. After the rollout completes, two things are extracted from the conversation transcript:
    • Search queries — parsed from the LLM's tool-call blocks (supports Anthropic tool_use, OpenAI function calls, and XML <tool_call> formats)
    • Evidence chain — parsed from <evidence_chain> tags in the LLM's final message, explaining how the discovered chunks connect to each other and to the primary
The query replay indirection

The LLM runs in a separate environment (the rollout server), so the search results it sees come back as text — not as chunk objects the pipeline can use directly. To bridge this gap, the pipeline takes the query strings the LLM searched for and replays those same queries against the local corpus. The returned chunks are the actual objects that go into the anchor bundle.

This means the LLM's value isn't in the specific results it found — it's in the queries it formulated and the evidence chain it articulated. The pipeline trusts the LLM's search strategy but verifies the results locally.

Post-search filtering (differs from metadata linker)

The same basic rules apply (400 char min, same-file exclusion, cross-question dedup, coherence floor), but the parameters differ:

  • Composite ranking: 60% search relevance + 40% Jaccard (vs. metadata's 40/30/30 split). There's no separate entity-overlap term — the LLM's query quality already encodes that signal.
  • Diversity cap: 0.8 Jaccard between secondaries (vs. metadata's 0.55). This is more relaxed because the LLM is trusted to have deliberately chosen different chunks.
  • Confidence score: a composite of 40% fulfillment (did we find enough secondaries?) + 30% survival rate (what fraction of search results survived filtering?) + 30% evidence chain quality (did the LLM produce a structured explanation of the connection?).
Fallback behaviour

If the LLM rollout fails for any reason (timeout, API error, no queries extracted), the search agent linker falls back to the metadata linker's result, flagged with llm_fallback: true in the structural hints. This ensures the pipeline never blocks on an LLM failure during linking.

Q6 Why does the search agent replay queries locally instead of using the LLM's search results directly?

The LLM runs on a rollout server — a separate environment that executes the agent loop. The search results the LLM sees during its rollout are rendered as text in its conversation (descriptions, snippets), not as the pipeline's internal Chunk objects with hashes, metadata, and content fields.

To get usable chunk objects for the anchor bundle, the pipeline needs to go through the local corpus source. The cheapest way to do that is to take the query strings the LLM used (which are already structured — they come from parsed tool-call blocks) and replay them against the same search index. The local search returns actual Chunk objects that carry the hash, metadata, and full content the pipeline needs downstream.

In practice this means the LLM's contribution is its search strategy — what to look for and why — not the raw results themselves. The evidence chain it produces also gets passed through to the QA generation prompt as a structural hint, giving the question-writing LLM context about how the chunks relate.

Q7 Where does the primary chunk come from?

The primary chunk goes through a three-stage funnel:

Stage 1 — The diverse profile pool

The starting pool is the 500–10,000 chunk sample built by diverse_profile_sample() (stratified by document + random fill, as described in Q3).

Stage 2 — Suitability scoring

Every chunk in the pool gets a 0–1 suitability score computed from six signals:

  • Metadata richness — does it have headers, doc IDs, dates?
  • Entity density — quality-weighted entity count per 1,000 characters
  • Lexical diversity — unique tokens / total tokens
  • Content length — character count
  • TF-IDF distinctiveness — how distinctive are its top keyphrases vs. the rest of the corpus?
  • Answerability — sentence density, markup ratio, boilerplate penalty (can you actually ask a question about this chunk?)
Stage 3 — Bottom-quartile filter + random sampling

Chunks below the 25th percentile suitability score are excluded. Seeds for each micro-batch are randomly sampled from the remaining top 75%. This avoids spending LLM calls on chunks that are too short, too boilerplate-heavy, or too entity-sparse to support a good question.

During regeneration, if a seed keeps failing, the pipeline can reanchor to a completely fresh chunk from the full corpus (not just the pool), so it's never stuck trying to make a bad seed work.

Q8 How are the two candidate scoring signals — search relevance (60%) and topical overlap (40%) — measured?
Search relevance (60% weight)

This is the score the search backend returns for each result. What it actually measures depends on the backend:

  • BM25 / lexical mode — a term-frequency score weighted by how rare each matching word is across the corpus. Common words like "the" contribute little; distinctive terms like "Sapphire" contribute a lot.
  • Vector mode — cosine similarity between the query embedding and the chunk embedding.
  • Hybrid mode — a fused score from Reciprocal Rank Fusion. Each result gets 1/(k + rank) from both the BM25 and vector rankings, and the scores are summed.

In all cases, it answers: how well did this chunk match what was searched for?

Topical overlap (40% weight)

This is the Jaccard similarity between the candidate chunk and the primary chunk — the same formula as the coherence floor, but used as a continuous score rather than a pass/fail threshold:

Jaccard = (shared words) / (total unique words across both chunks)

It answers: how much vocabulary does this candidate share with the primary chunk? This is independent of the search query — it's a direct chunk-to-chunk comparison. A higher overlap means they're talking about related topics.

The two signals complement each other: search relevance says "this chunk matched the query well" while topical overlap says "this chunk is actually about a related topic to the primary." A chunk could score high on search relevance (matched a specific keyword) but low on topical overlap (otherwise about a completely different subject), and the composite score would reflect that.

Q9 How does the "Retrieval Too Easy" filter work, and what are "reference chunks"?

The reference chunks are the chunks that were used to generate the question — the anchor bundle (primary chunk + secondary chunks). They're stored alongside each QA pair as the ground-truth evidence.

The filter checks whether a naive search using just the question's own words already turns up the answer. It works in two layers:

  1. Overlap check — the filter searches the corpus using the question text and checks how many of the returned results overlap with the reference chunks. If the overlap is high, the question is immediately flagged as too easy.
  2. LLM judge — if the overlap check passes, an LLM judge is given only the question and the search results (not the reference chunks), and asked: "can you answer this from what's here?" If yes, the question is too easy.

The logic is: if a basic RAG system would retrieve the right information on the first try, the question doesn't actually test multi-hop reasoning. A good multi-hop question should require finding and combining specific chunks that a simple search wouldn't surface together.

Q10 What exactly is a multi-hop question, and how does the pipeline enforce that requirement?

A multi-hop question is one where no single document contains the complete answer. You need information from multiple separate documents and have to combine them to reach the answer.

For example: "Can I use Chase Sapphire points to book a Southwest Companion Pass trip?" To answer this, you need the Sapphire benefits page (which lists Southwest as a transfer partner) and the Southwest Companion Pass page (which explains how the pass works and whether transferred points qualify). Neither page alone answers the question.

Two filters enforce the multi-hop requirement — from opposite directions

The pipeline uses two complementary filters to ensure generated questions are genuinely multi-hop:

  • Retrieval Too Easy (filter 3) — asks: is this question hard to retrieve? It runs a simple search using the question text and checks whether the right chunks show up. If a basic keyword search already surfaces the answer, the question doesn't test multi-hop reasoning — a naive RAG system would get it right on the first try.
  • Hop Count Validity (filter 5) — asks: is this question hard to answer from a single source? An LLM judge examines whether the question genuinely requires combining information from multiple documents, or whether it just looks multi-hop but can actually be answered from one chunk.

A question must pass both — hard to find (resists simple retrieval) and hard to answer without cross-document reasoning (genuinely requires multiple hops).

Q11 Does a 2-hop question always have exactly 2 golden chunks?

Currently, yes. The linker uses n_secondaries = hop_count - 1, so a 2-hop question always gets 1 primary + 1 secondary = 2 chunks. The hop count validity filter also equates chunk count with hop count (hop_count_claimed = len(reference_chunks)).

But this conflates two things that aren't the same. "Hop" should mean distinct documents needed, not number of chunks. A richer 2-hop question might need several pieces of evidence from each of the two articles — e.g. one chunk about eligibility rules and another about fees from the same article, combined with a chunk from a second article.

Design issue — three places where chunk count is used as hop count
  • Linker formula — n_secondaries = hop_count - 1 caps to one chunk per hop. Should instead find chunks from hop_count - 1 distinct documents, returning multiple per document if needed.
  • Same-file exclusion — the linker's filter pipeline excludes all same-file chunks. This is correct for the primary's document (forces cross-document hops), but once a secondary document is chosen, other chunks from that same document should be allowed if they're relevant.
  • Hop count validity filter — hop_count_claimed = len(ref_chunks) should count distinct document IDs, not chunk count.

The correct behavior: a 2-hop question should be allowed to have more than 2 golden chunks, as long as they come from exactly 2 distinct articles.

Q12 What determines whether a failing question is rejected (permanently dropped) vs sent to regeneration?

Two levels work together:

Level 1 — The filter decides if the failure is fixable

Some failures are fundamentally unsalvageable — the filter rejects outright, no second chance. For example: the "question" is a bare noun phrase with no verb, or it asks about page layout instead of content. No amount of rewriting will fix these.

Other failures are potentially fixable — a thin answer, too-easy retrieval, a redundant chunk. These get a verdict of needs_refinement instead.

Level 2 — A per-item budget caps how many chances it gets

Each item tracks how many times it's already been refined (refinement_count). If refinement_count < max_refinements_per_item (default 2), the filter returns needs_refinement. If the budget is exhausted, it returns rejected — the item has had its chances.

On top of that, the pipeline loop itself has a max_rounds cap (default 4). Even if a filter says needs_refinement, once the loop has iterated that many times, all remaining unresolved items are force-rejected.

Per-filter breakdown
  • Deterministic Guards — always rejects. Structural failures (too short, wrong language, chunk overlap) have no refinement path.
  • Quality Gate — rejects fragments, meta-doc questions, and guide-pointer answers outright. But thin answers get sent to refinement ("provide a more detailed answer").
  • Retrieval Too Easy — always refinable (budget permitting). The hint is to rewrite the question to reduce lexical overlap with the source chunks.
  • Grounding LLM — always refinable (budget permitting). If the answer isn't supported by the chunks, the item is sent back with a reanchor flag and a hint to reground the answer in chunk evidence.
  • Hop Count Validity — always refinable (budget permitting). Redundant or low-contribution chunks trigger a rewrite to make all chunks essential.

The logic is: can this plausibly be fixed by rewriting? If yes, give it another shot (up to the budget). If no, drop it immediately.
